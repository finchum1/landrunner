# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Stack

Next.js + Tailwind, same stack as the Latchpoint Studios sites (user chose "Next.js like Latchpoint"). New folder, new GitHub repo, new Vercel project, multi-page. Domain not decided.

## Users

Landmen and leasing agents (independent or at small leasing firms) who call mineral owners to lease their mineral rights for an operator. They work from ownership reports/title spreadsheets, make dozens to hundreds of calls, send offer letters, and report progress to an operator or boss. Today most of them do this in spreadsheets and email.

## Product Purpose

JillSpoon Leasing (working/placeholder name; previously "Landrunner") is a web app for landmen to run a mineral-lease project: import the owner spreadsheet, work a call queue, log call outcomes, schedule follow-ups, generate offer letters, track bonus payments, bill hours and mileage against a prospect number, and send the operator a status report. Success for the site: a landman understands in one scroll that it replaces their spreadsheet, and asks to use it.

## Positioning

Built by a working landman for the way a leasing project actually runs (an ownership spreadsheet, a prospect number for billing, an operator who wants a weekly status), not a generic CRM. The call queue puts the biggest net mineral acres and the due follow-ups first.

## Operating Context

A project = one section/township/range in a county for one operator, with a prospect number used for billing. Owners are imported from a title-opinion or ownership spreadsheet (name, interest, net mineral acres, notes). Offers are per net mineral acre bonus plus a royalty, e.g. a one-year paid-up lease, with an optional extension. Offers expire after a set number of days. Statuses run not contacted -> attempted -> contacted -> offer made -> negotiating -> leased / declined / unresponsive / client.

## Capabilities and Constraints

Built and live today (as the app "Landrunner"): multi-project tracking; spreadsheet import and safe re-import (match by name, fill blanks); owner table with status counts, sort, filters, bulk actions, Excel export; call outcomes that move status and set follow-up dates; call queue; wrong-number and do-not-contact flags, extra phone numbers; dashboard of due follow-ups across projects; offer letter generation to Word (.docx) from the project's terms, one page per owner; per-owner terms tiers; lease bonus due/paid tracking; file attachments per owner; client status report (print/PDF + Excel); prospect billing (hours, mileage, expenses, invoice print/Excel, mark billed); light/dark themes; mobile layout.
Single user today (Terrence). Multi-user, daily email/calendar reminders, heirs/family grouping are NOT built. Pricing, signup, and public availability are undecided: the site must not state prices or claim open signup.

## Brand Commitments

Name: JillSpoon Leasing (placeholder, may change; keep it easy to swap). The app currently uses an amber/stone palette; no commitment to keep it. The user wants the site to feel related to the Latchpoint sites (Next.js, craft level) but explicitly "not just look like those".

## Evidence on Hand

Real: the working app (screens can be captured with sample data), a real offer-letter template and status report layout generated by the app. Absent: testimonials, customer names, usage numbers, pricing, case studies. Do not fabricate any of these; the only honest social proof is "built by a working landman".

## Product Principles

1. Speak landman: net mineral acres, prospect number, bonus per acre, royalty, offer expiry, division order. Never generic CRM language.
2. Show the real workflow (spreadsheet in, calls, offers, report out) with sample data, never invented customers or numbers.
3. One clear action: ask to get access / early access, since signup and pricing are not open.
4. The name is a placeholder: nothing in the design should depend on it being permanent.

## Accessibility & Inclusion

Standard WCAG AA contrast, keyboard navigable, respects prefers-reduced-motion. Many users are on phones in the field, so mobile must be first-class.
